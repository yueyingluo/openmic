# OpenMic 产品需求文档（立项讨论版）

- 文档状态：Draft
- 负责人：组长（待填写姓名）
- 版本：v0.1
- 课程要求：[OpenMic 项目页](https://yzhu.io/courses/core/projects/openmic/)
- 本文目的：统一目标、接口和验收口径；不是提前锁死每位成员的实现方案。

## 1. 背景与问题

用户通常只会提供一句生活主题，但一段可表演的中文脱口秀还需要主题扩展、受众适配、setup-punchline 创作、节奏设计、质量控制和语音合成。单次大模型调用难以同时稳定满足这些约束，因此项目采用职责分离的多智能体协作流程。

## 2. 产品目标

输入主题、表演风格、目标时长和目标受众，系统在一次端到端流程中产出：

1. 3–5 分钟中文脱口秀脚本；
2. 明确的铺垫、包袱、回调和表演标记；
3. 可播放、可导出的 16 kHz 语音；
4. 可视化的 Agent 协作记录与质量评分。

## 3. 非目标

- M0 不训练模型，不追求生成内容真实好笑；
- M0 不实现生产级用户系统和高并发；
- 不让 Agent 无限制自由讨论；每次重写次数必须有上限；
- 不在仓库中提交 API Key、原始受限数据或大模型权重。

## 4. 目标用户与核心场景

**目标用户**：希望快速生成中文脱口秀样稿的普通用户，以及现场验收项目的教师。

**核心场景**：用户输入“我的网购经历”，选择“吐槽”、3 分钟、大学生受众；系统展示五个 Agent 的处理过程，输出脚本和语音，并允许重新生成与导出。

## 5. 输入与输出契约

### 输入

| 字段 | 类型 | 必填 | 约束 |
|---|---|---:|---|
| `topic` | string | 是 | 非空生活主题 |
| `style` | enum | 是 | 观察 / 自嘲 / 吐槽 |
| `duration_minutes` | int | 是 | 3、4 或 5 |
| `audience` | string | 是 | 如大学生、职场新人 |

### 输出

| 输出 | 最低要求 |
|---|---|
| Agent 轨迹 | 角色名、输出摘要、耗时、错误状态 |
| 脚本 | 分段文本，标出 setup、punchline、callback |
| 表演标记 | 停顿、重音、语速、情绪 |
| 质检结果 | 幽默度、文化适配、结构完整性、通过/修改 |
| 音频 | WAV，16 kHz，可播放和导出 |

## 6. 多智能体流程

| Agent | 输入 | 输出 | 完成标准 |
|---|---|---|---|
| ComedyDirector | 用户需求 | 主题扩展、叙事主线、风格边界 | 策略可被下游直接引用 |
| AudienceAnalyzer | 用户需求、策略 | 共鸣点、禁忌、语言偏好 | 包含风险提示 |
| JokeWriter | 策略、受众结论、CFunSet 示例 | 结构化脚本 | 有 setup-punchline 和至少一次回调 |
| PerformanceCoach | 脚本 | TTS 可执行表演标记 | 停顿和重音位置明确 |
| QualityController | 全部结果 | 多维评分、修改意见、是否通过 | 输出结构化结果 |

质检不通过时回到 JokeWriter，随后再次经过 PerformanceCoach；最多重写 2 次，防止死循环和成本失控。

## 7. 功能优先级

### P0：必须完成

- 五个 Agent 和有序 GroupChat；
- CFunSet 数据读取、检索或训练数据构造；
- 3–5 分钟结构化中文脚本；
- 带停顿、重音、情绪控制的 TTS；
- Streamlit 页面、脚本展示、语音播放、重新生成、导出；
- 五个主题样例、技术报告、评估结果、10 分钟演示视频。

### P1：有余力再做

- FastAPI 前后端分离；
- Prompt 与 LoRA 的对照实验；
- 自动化离线评测面板；
- 多种 TTS 模型或声音对比。

## 8. 指标与验收

| 类别 | 指标 | 目标 |
|---|---|---:|
| 内容 | 脚本时长 | 3–5 分钟 |
| 内容 | 幽默度、文化适配、结构完整性 | 明确量表并报告均值 |
| 语音 | 采样率 | 16 kHz |
| 语音 | 实时率 | > 1.0x |
| 语音 | MOS 与表演效果 | 完成盲评并报告人数与方差 |
| 系统 | 生成响应时间 | < 30 秒（需在报告中明确统计边界） |
| 系统 | 稳定性 | 演示流程连续运行无崩溃 |

## 9. 技术方案（待会议确认）

- Python 3.9+；
- AutoGen：已决定使用 0.2，锁定 `autogen-agentchat~=0.2`，对应课程要求的 `ConversableAgent` / `GroupChatManager`；
- 模型：DeepSeek OpenAI-compatible API，先 Prompt baseline，再决定是否做 LoRA；
- 数据：CFunSet 为核心，明确许可证、划分、清洗和检索/训练方案；
- TTS：先比较 ChatTTS 与可用替代方案，再固定主模型；
- UI：优先 Streamlit，只有在接口复用确有需要时增加 FastAPI；
- 测试：Mock 引擎进入 CI，真实模型与 TTS 使用单独 smoke test。

## 10. 建议分工（会议讨论稿）

| 角色 | 建议主责 | 主要交付物 |
|---|---|---|
| 组长 / 成员 A | 架构、AutoGen、接口、集成、进度 | 主流程、接口契约、集成版本 |
| 成员 B | CFunSet、主题扩展、幽默生成 | 数据管线、Prompt/LoRA baseline |
| 成员 C | TTS 与表演控制 | 语音管线、节奏/情感实验 |
| 成员 D | QualityController 与评测 | 评分器、人工评测表、实验报告 |
| 成员 E | Streamlit/FastAPI、Demo 与导出 | UI、过程展示、演示脚本 |

原则：每个模块一位主责、一位 Reviewer；最终演示和报告不是某一个人的“收尾杂活”。

## 11. 里程碑

| 里程碑 | 目标 | 退出条件 |
|---|---|---|
| M0 骨架 | 全员可开发 | Mock 端到端、测试、PR 流程可用 |
| M1 文本 baseline | 真模型产出脚本 | 五 Agent 跑通，保存轨迹和结构化脚本 |
| M2 语音 baseline | 文本转可控语音 | 16 kHz 输出，有停顿/重音控制 |
| M3 评测与 UI | 可完整演示 | 页面、五主题样例、量化和人工评测 |
| M4 交付 | 课程验收 | 报告、代码、音频、10 分钟视频齐全 |

具体日期在确认课程 Deadline 后填写，避免写一份看似完整但无法执行的排期。

## 12. 主要风险

| 风险 | 影响 | 应对 |
|---|---|---|
| AutoGen API 版本不一致 | 全组环境和代码冲突 | 第一周确认并锁版本 |
| 五次以上串行 LLM 调用超过 30 秒 | 不满足性能目标 | 缓存、并行可并行步骤、限制轮数、轻量模型 |
| “好笑”缺少可复现标准 | 报告说服力弱 | 自动量表 + 盲评 + baseline 对照 |
| TTS 环境或显存不足 | 无法稳定演示 | 尽早做本地/云端 smoke test，保留预生成兜底 |
| 数据版权或许可不清楚 | 无法公开仓库或样例 | 开始前核对许可证，只提交允许公开的内容 |

## 13. 开放问题

1. 内容生成“<30 秒”是否包含 TTS 时间？
2. CFunSet 的使用重点是 RAG、Prompt 示例、SFT/LoRA，还是可以自行选择？
3. 组内可用 API、GPU、预算分别是多少？
4. 仓库最终公开还是保持私有？数据和音频是否允许公开？
